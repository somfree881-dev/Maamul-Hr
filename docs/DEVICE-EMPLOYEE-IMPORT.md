# Device employee import and historical mapping

## Activation (manual approval/deployment only)

1. Review `supabase/migrations/202610250003_device_employee_import.sql`. Apply this new migration once in your Supabase SQL Editor or your normal reviewed migration deployment. Do not rerun the initial installer. It depends on the existing foundation/workflow tables and functions, not the optional login-name feature. It adds a private staging table, indexes and explicitly granted RPCs; it does not delete or reset employees, mappings, raw events or payroll.
2. Build/deploy the updated Next.js application. Its server-only Supabase service-role key must already be configured for connector ingestion. Do not put it in the Python configuration or any NEXT_PUBLIC variable. The user-facing import API still uses the authenticated user's Supabase client and database authorization.
3. Update the Windows connector by running `connector/Setup-WindowsConnector.cmd` (or the existing installer in Administrator PowerShell) after approval. The installer copies the updated connector code and preserves the installed queue, device IDs and credentials. Do not generate/rotate tokens for this feature. If source configuration/credentials were changed since the last install, reconcile them with the installed configuration before reinstalling. No installer was executed automatically for this feature.
4. Check each existing `devices.json` entry. K14 must use the registered Dabka device UUID, IP, timezone and its own token environment variable. UF100Plus must retain its registered NO4 UUID and its separate token. Add future devices using the same existing configuration format. This feature does not rewrite either configuration file or any enrollment hash.
5. In Maamul HR, sign in as Company Admin, Super Admin or HR Manager. Open Devices & Integration and click **Import Employees from Device** on the correct device row. The dialog is private; Branch Manager, Supervisor, Accountant and Employee roles cannot perform imports. Existing branch-scoped attendance permissions remain unchanged.
6. Click **Request device users**. The connector polls for a pending request and reads a full roster using `get_users()`. Wait for **ready**; the dialog refreshes every five seconds while waiting. The computer, device and API must be reachable. An unreachable UF100Plus produces an import error without changing employee profiles. Restore LAN access and request a fresh snapshot when ready.
7. Review new-user, existing-match, conflict, historical-log and unmapped-log counts and every row's decision. Keep suggested matches only after confirming identity. Select an existing employee from the same company/branch or skip conflicts. Existing mappings cannot be reassigned through this import. Duplicate/blank names require manual resolution; they are not silently created.
8. For new profiles, enter the actual employment start date. Imported profiles start **inactive**, with **zero salary**, in the device's registered company/branch. No email, Auth account, password, app role, shift, salary payment or payroll run is created from device data. Review HR details, salary and shifts separately before payroll. Single-word names remain preserved with an empty last-name field for later HR completion.
9. Tick the explicit review/approval checkbox and click **Confirm import and map history**. Results show created/linked/skipped employees, mappings created, historical events mapped and the remaining unmapped count. The result remains available when reopening the dialog. There is no employee creation before this confirmation.
10. For attendance details, select the original work dates and process attendance as usual. Mapping raw history does not rewrite existing summaries or change finalized payroll. Historical punches outside an employee's confirmed employment range remain raw history and are not automatically treated as payable work.

## Data and security behavior

- Python reads only `user_id`, `name` and `group_id`; only these allowlisted fields are serialized. Passwords, card numbers, privilege flags, fingerprint templates and face data are neither inspected by the serializer nor uploaded. No `get_templates`, enrollment, write-user, delete-user, clear-attendance or disable-device operation is called. pyzk's user object may internally contain other vendor fields; they are never persisted or transmitted by this feature. Supported devices must support pyzk's read-only `get_users()` operation; ADMS/vendor-specific readers need their own compatible metadata adapter.
- Machine messages use the existing per-device bearer token and constant-time SHA-256 comparison. Device keys cannot approve imports or poll another device's request. Company and branch are derived from the registered device, never accepted from metadata uploads. Browser requests require session, origin, company membership, authorized role and RLS/RPC checks. Preview data is not public.
- Matching priority: an existing device mapping; otherwise an exact employee number/device user ID or normalized full name within the company. Only an unambiguous employee in the device branch is suggested. Other-branch matches, repeated names and blank names become conflicts. Matching never overwrites an existing employee's fields. An administrator explicitly confirms creation/linking/skipping.
- Confirmation locks the snapshot and serializes matching with employee writes. Its version token detects changed employee/mapping matches and requires a fresh review. Mapping uniqueness and imported-request results make repeated confirmation idempotent. A short employee-table lock prevents concurrent creation from invalidating the reviewed matching decision; schedule very large imports outside busy hours. The snapshot limit is 20,000 users, uploaded in batches of at most 500.
- Roster batches persist in the connector's existing protected SQLite state with acknowledged offsets. Network failures retain the snapshot for retry. A completed, failed or cancelled request stops accepting metadata. Permanent validation errors become a safe import error; tokens and names never go into logs. The existing startup service's protected state ACLs also cover the added local queue table. Successful metadata delivery removes the local staged roster; database snapshots remain private for review/audit.
- Historical punches retain their original occurred_at/source_key. The existing connector uses each device's configured IANA timezone to interpret naive device timestamps. No historical timezone or raw timestamp is rewritten by importing employees. Correct the device clock/timezone separately if its clock was wrong; this feature does not invent corrected times.
- History linking updates only NULL employee associations for matching `(device_id, device_user_id)` within the registered company. It does not reassign already linked events, recalculate payroll or alter paid salary records. Repeated attendance delivery still uses the existing unique device/source-key constraint. Unknown/skipped/removed device users remain visible in the unmapped count.
- There is one active snapshot per device. Request/refresh retries reuse it; cancel it explicitly to collect a changed roster. Company/branch changes invalidate a snapshot, which must be cancelled and requested again. Device imports are independent per device and do not block other device attendance synchronization.

## Validation

Run `npm test`, `npm run build`, `connector/.venv/Scripts/python.exe -m unittest discover -s connector -p "test_*.py"`, and `npm run test:db` (isolated local PostgreSQL, configurable MAAMUL_TEST_DB_PORT).

Fixtures model 22 users and 418 historical punches, including an existing employee, ambiguous/blank identity, another company/branch, replayed snapshots, stale previews and partial batch retries. They verify no pre-confirmation creation, no salary overwrite, unchanged timestamps, repeat-safe imports and remaining unmapped logs. These are synthetic fixtures, not a claim that your real K14 users/logs were imported. Production migration application, Windows service deployment and physical-device acceptance remain explicit activation steps.
